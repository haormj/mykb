# Design

## Context

第一阶段已把后端改为知识库作用域并提供成员/鉴权接口，第二阶段提供文档导入。前端仍保留全局评测/审核/看板入口，且缺少设置与成员管理界面。本变更做前端整合，不改后端 spec 级行为。See `proposal.md - Why`.

## Goals / Non-Goals

**Goals:**
- 所有功能都在具体知识库上下文内访问，移除全局入口。
- 知识库详情成为完整工作台：文档、知识、评测、审核、看板、设置。
- 设置页覆盖基础配置、远程仓库补绑、成员与角色管理。
- 界面按当前用户角色隐藏无权操作。

**Non-Goals:**
- 不新增或改变后端 spec 级行为；只消费已定义接口。
- 不实现新的导入/评测/审核逻辑。

## Decisions

### 1. 路由结构

```
/login
/kbs                         知识库列表（新建）
/kbs/:kbId/documents         文档（来自②）
/kbs/:kbId/knowledge         业务知识（只读投影 + 状态/血缘）
/kbs/:kbId/evals             评测集与运行
/kbs/:kbId/review            草稿审核
/kbs/:kbId/scores            分数看板
/kbs/:kbId/settings          设置（基础 / 远程 / 成员）
```

- 顶层导航只剩「知识库」与用户菜单；评测/审核/看板成为知识库详情内的 tab。
- 未登录访问任意受保护路由跳转 `/login`；无权访问的知识库显示 403 提示并引导返回列表。

### 2. 角色感知的界面

- 知识库详情接口返回当前账号在该库的角色（`my_role`）与可执行能力。
- 按能力矩阵控制按钮可见/可用：viewer 只读；editor 出现导入/起草/评测；admin 出现审核/设置/成员；owner 出现删除/转移/改远程。
- 角色变更后重新拉取详情，避免界面权限与后端不一致。

### 3. 设置页

- **基础**（admin）：名称、分支等可由 admin 修改的字段。
- **远程仓库**（owner）：补绑远程，展示当前 `git_url` 与最后推送状态；仅允许空远程。
- **成员**（admin）：成员表格、添加成员、调整角色、转让 owner；越权选项禁用并提示。

### 4. 只读投影，不新增 spec

- 「知识」页对已存储的 `knowledge` 概念做只读展示（标题、状态、血缘），属于既有存储行为的投影；若需要列表接口，仅以只读方式暴露既有数据，不引入新 spec 能力。

## Risks / Trade-offs

- **前端权限仅为体验层** → 真正的授权仍在后端；缓解：所有写操作继续由后端 `require_kb_role` 校验。
- **角色缓存过期** → 缓解：进入页面与操作后重新拉取知识库详情。
- **深链到无权知识库** → 缓解：统一 403 兜底页。
- **移除全局入口影响现有用户习惯** → 缓解：保留知识库列表作为首页，文案引导。

## Migration Plan

1. 随第一、二阶段后端就绪后上线前端路由与页面。
2. 移除全局评测/审核/看板导航，改为知识库内 tab。
3. 回归：各角色可见性、设置/成员操作、深链 403。

## Open Questions

- 「知识」页是否需要编辑能力，等真实使用反馈再定（当前只读）。
